### 问题 2：网络代理有没有可能？

**我确实没考虑到，谢谢提醒。已做对照实验验证：代理不是原因。**

| 路径 | 握手 | 数据调用 | 结果 |
|---|---|---|---|
| **直连（绕过代理）** | ✅ 298ms | `service temporarily unavailable` | 到达服务层 |
| **走代理 127.0.0.1:17891** | ✅ 223ms | `service temporarily unavailable` | 到达服务层 |

**两条路径行为完全一致** —— 如果是代理问题，两者必然不同。

补充说明（技术细节，供参考）：
- 您的系统代理是开启的（注册表 `ProxyEnable=1`, `127.0.0.1:17891`）
- Node.js 的 `fetch` **默认不读系统代理**，只认 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量
- 所以我们的直连请求是绕过代理的；贝壳 CLI（Rust）会读系统代理
- 我用 `EnvHttpProxyAgent` 显式走了代理做对照 —— 结论是两条路都通

**结论：代理不需要调整。**

## 三、修复的 5 个真实 bug

### Bug 1：直连调用报 `-32602 Invalid request parameters`（我的 bug）

`notifications/initialized` 是 JSON-RPC **通知**，不能带 `id`。
我带了 → 服务端返回 -32602 → 我的 `doHandshake()` 抛异常 → **整个握手失败**。

**定位方式**：三组变体对照实验（带 id / 不带 id / 跳过通知）。

### Bug 2：`BigInt(undefined)` 崩溃（真实影响"搜不到"）

```js
if (query.budgetMax !== null) { where['totalPrice'] = { lte: BigInt(query.budgetMax) }; }
```

类型声明是 `number | null`，但**运行时可能是 `undefined`** →
`BigInt(undefined)` 抛 `TypeError` → **整个缓存降级路径崩溃** →
永远报"本地没有可用的缓存房源"。

**这就是"以前能搜到，现在不行"的一个直接原因。**

### Bug 3：缓存检索没有城市过滤（跨城市错误推荐）

原实现只按行政区/板块过滤，**没按城市**。后果：本地有 41 套上海房源时，
客户搜"厦门"会匹配到这 41 套上海房源 —— **把上海的房子推荐给想买厦门的客户**。
这比"搜不到"更糟，因为经纪人可能真发给客户。

### Bug 4：`preferredCity` 默认值压掉客户原话

```prisma
preferredCity  String  @default("上海")
```

我写的第一版优先级是 `cityOverride ?? existingProfile.city ?? customer.preferredCity`，
于是**新客户说"想看厦门思明区三房"，被一个默认值压成了上海** →
产生"上海 + 思明区"这种自相矛盾的条件。

**修正后的优先级**：经纪人选择 > **客户本次原话** > 已有画像 > 客户资料。

### Bug 5：`cityOverride` 没覆盖到搜索条件

我只把 `cityOverride` 用在需求抽取的提示上，**忘了覆盖 `searchProfile.city`**，
而查询构造器读的是 `searchProfile`。结果：界面显示了筛选标签，
实际搜索条件仍是画像里的城市 —— 结果与选择完全不符。

**教训**：**"提示"与"生效值"是两回事**。

## 五、关于"用爬虫爬别的平台"

### 我不会实现自动爬取，理由如下

您提到的方案是"贝壳找不到就用爬虫爬别的平台"。**技术上我能做，但法律上不能做。**

这不是保守，是有明确判例的：

> **链家/天津小屋 诉 北京/成都神鹰城讯（推推99）**
> 海淀法院一审判决**赔偿 550 万元**（500万 + 50万），上诉撤回，**判决已生效**，
> 并发出行为禁令。
>
> 法院明确认定：**"涉案数据虽是二原告向公众无差别的予以提供和展示的公开数据，
> 但这并不意味着其他经营者可以不受任何限制的获取和使用。"**

**为什么这个判例特别相关**：被认定的侵权模式是
"抓取 → 存到自己的服务器 → **去掉水印** → 展示/下载/转发"，
这**就是**一个标准的房源数据 SaaS。而我们的产品形态与之高度相似。

**而且风险会传导到您**：判决还提到下游使用会成为责任来源
（"为发布虚假房源提供了重要工具和便利条件"）。
也就是说，**用爬来的数据推荐房源，风险由您的公司承担，不是由我承担**。

### 我建议的替代方案（合法且更实用）

| # | 方案 | 说明 | 状态 |
|---|---|---|---|
| **1** | **经纪人手动录入** | 您在别的平台看到房源，**自己填进来**。个人查阅公开信息不违法；系统只是您的笔记本 | ✅ 后端已就绪，**UI 待做** |
| **2** | **官方 API 授权** | 贝壳/安居客的企业合作 | ⏸ 需商务谈判 |
| **3** | 公司自有房源 | 独家盘、委托盘 | ✅ 已支持 |

### 我的建议：先做方案 1

理由很实际：
- **零法律风险**
- **立刻可用** —— 后端（`UserProvidedPropertyProvider` + 导入接口）**已经实现并验证过**
- 缺的只是一个让经纪人点得到的界面
- 而且您作为厦门本地经纪人，**手上的独家盘/委托盘本身就是最有价值的房源**，
  比爬来的公开数据更能成交

做完之后，您在别的平台看到的房源可以 30 秒录进来，
系统会明确标注"经纪人录入 · 需人工确认"，不会假装它是实时验证过的。
